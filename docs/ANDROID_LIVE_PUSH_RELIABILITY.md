# Android — Live started mobile push delivery (draft)

Existing behavior retained: approved creators starting a live trigger
LIVE_STARTED over Socket.IO for online followers, sendMulticastPush to at most
500 followers with category live, and create persisted in-app notifications.
Android has a "lives" channel. Notification taps route to /live/{liveId}.
These are not global broadcasts. The follower must allow notifications and
enable the "live" category. A logged-out or blocked user receives none.

Bug fixed: email/password login uses setToken() without necessarily triggering
a NextAuth session change. The global providers effect previously depended on
session and could miss native FCM registration. A no-payload event now triggers
registration after any setToken; foreground rechecks at most once every five
minutes. This does NOT ask permission without user action or change authentication.
Registering a token with backend also checks the HTTP response status, not
just network failures, so 401/429/5xx cannot be silently called success.

## Persistent notification preferences and device permission

- A new user begins with enabled notification categories, but user choices
  remain authoritative. An explicit empty categories array is NOT reset to
  the default on GET and does NOT match an FCM "live" category filter.
- Android OS permission is checked *before* a cached Firebase token can be
  re-sent with permissionStatus=granted. Revocation cannot be silently
  represented as consent. Notifications can be re-enabled only by the user.
- Android still owns the final permission/channel behavior, including Doze
  scheduling; "always active" cannot mean guaranteed or forced delivery.

## Time-sensitive Android Live push delivery

The already existing FCM visible notification now requests Android `high`
priority for `type=live`, using the supported Firebase Admin AndroidConfig
API. TTL is 15 minutes, preventing delayed notifications from arriving many
hours after the creator starts streaming. This only affects Live push payloads;
all other categories retain their previous FCM urgency and device channels.
Tests assert both Live behavior and non-Live unchanged.

**Limits and precautions:** high priority is a delivery hint, not a
guarantee and must only be used for user-visible opted-in Live alerts.
FCM can delay/throttle excessive high-priority messages; user OS permission
and per-category preferences remain authoritative. No push is generated by
this code change. Physical phone/FCM test still pending.
